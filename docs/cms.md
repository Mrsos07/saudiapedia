# Payload CMS operations

## Integration contract

This backend uses the installed Payload 3.89.0 packages, PostgreSQL, Next.js App Router and structured textarea content (no Lexical or custom client components). `/admin` and `/api/[...slug]` live under the separate `(payload)` root layout. The application integrator must provide `withPayload` in Next config, the `@payload-config` alias, and move the frontend under its own root route group **without a shared `src/app/layout.tsx`**. These changes and package installation are outside this backend's scope.

The empty `admin/importMap.ts` is intentional. Automatic import-map and type generation are disabled to avoid unexpected generated files. If custom components are added later, run Payload's generator and review its output. Admin interface translations support Arabic and English; article languages are separate documents, not Payload field localization.

The CMS root imports `@payloadcms/next/css` followed by `admin.css`. Installed `RootLayout` accepts `htmlProps`, not a custom `head` prop. Admin CSS imports the supplied Zain Google Fonts stylesheet once and overrides Payload's font variables and form controls for both languages; the setup screen shares that CSS and has no duplicate font link. This makes external requests to `fonts.googleapis.com` and `fonts.gstatic.com`, with a sans-serif fallback if blocked. The separate public root's font link is unchanged. Both layout metadata and the configured/unconfigured admin page metadata remain `noindex, nofollow`; robots directives are not authentication.

## Run without a CMS

Leave **both** `DATABASE_URL` and `PAYLOAD_SECRET` empty (whitespace counts as empty). Public `getCMSEntries()` returns `null`; `/admin` displays a Zain-font setup page with a link to `/ar`, no credentials form, and no database initialization. REST methods return HTTP 503 JSON with `private, no-store` and `X-Robots-Tag: noindex, nofollow`. Runtime imports of Payload config, admin layout and page occur only after the environment guard. If only one setting is present, the guard throws a clear error naming the missing configuration requirements, without echoing values. Secrets shorter than 32 trimmed characters fail **before** importing config. Length validation does not prove randomness: generate the secret securely. A connection failure or incomplete S3 setup is a real configuration error, **not** a reason to silently serve seed data.

## Local configuration and bootstrap

1. Provision an existing PostgreSQL database and an application database user. The adapter does not create databases. Create `.env.local` with the settings below; fill values locally or through a secret manager, never chat or a web setup form. Do not copy historical provisioning files that may contain operational secrets.
2. `DATABASE_URL`: a PostgreSQL connection string. Use provider-required verified TLS in production; never disable certificate verification as a workaround.
3. `PAYLOAD_SECRET`: at least 32 cryptographically random characters, e.g. generate 32 random bytes with a password manager or Node's `crypto.randomBytes(32).toString('hex')`. There is no default secret. Keep it stable across replicas and deployments; rotation invalidates auth tokens.
4. `CMS_SERVER_URL`: the actual origin, without a trailing slash/path. Local default is `http://localhost:3000`. Production requires an explicit HTTPS origin. CORS and CSRF are limited to this origin; do not add wildcard origins.
5. Start the existing development command. Development schema push is off unless `CMS_DB_PUSH=true`; use only with a disposable development database. Local uploads live in `private-uploads/`, **outside `public/`**, and are served only through Payload access checks. Do not commit that directory; the integrator must add it to `.gitignore`.
6. **Before exposing the configured site to the Internet**, restrict `/admin` and `/api/users/first-register` to the operator (private network, maintenance gate or reverse proxy allowlist). Bootstrap is disabled by default. Only behind that private gate, temporarily set `CMS_ALLOW_BOOTSTRAP=true` and use Payload's built-in create-first-user screen at `/admin`; remove the flag immediately afterwards. The very first account is forced to `administrator`, irrespective of supplied role. A hidden unique bootstrap singleton prevents concurrent initial registrations from both succeeding. Ordinary anonymous POST `/api/users` is denied even when no users exist. The built-in first-register operation refuses requests once any user exists.
7. Confirm administrator login, then create editor, translator and reviewer accounts from Users. Ordinary user create/update is administrator-only, including role changes; user deletion is disabled so an empty user table cannot accidentally reopen bootstrap. Never clear the users table on a public service. Password login is limited to three attempts with a one-hour lock and two-hour tokens. Production cookies are secure and SameSite=Lax.

New passwords require 15–128 characters; existing login passwords are not changed. An administrator password update clears that user's sessions. No email provider is configured, so forgot-password and reset-password operations are explicitly disabled. Password-reset emails, invitations and delivery monitoring require a separate mail integration and review of the recovery guard; do not promise email recovery until it is tested. Administrators can manage user passwords. Account deletion and self-service profile/password editing are intentionally unavailable through regular collection updates.

Password hashing remains an open security item: the installed Payload 3.89.0 native generator and verifier use PBKDF2-HMAC-SHA256 with 25,000 iterations, below the current OWASP recommendation of 600,000 for this algorithm. The input-length policy does not upgrade stored hashes. Do not edit vendor constants in place: plan a versioned authentication migration or identity-provider integration and verify legacy-account compatibility in staging before changing live authentication.

## Editorial contract

- **administrator**: users, all editorial work, approval/publication and deletion.
- **editor / translator**: create/read/update articles, research sources and images; never newly approve or publish.
- **reviewer**: editor capabilities plus approval/publication, media release and version restoration; no user/role management.
- Anonymous article reads (REST and access-respecting Local API, including list and ID reads) require `_status=published` **and** `reviewStatus=approved`, plus a complete matching Arabic/English pair. Version history and source-library records require an editorial account. Reviewer user relationships are private.

Create an Arabic and English article with identical section, ASCII slug and stable translationKey. A UUID key is provided on creation; **copy that key into the other translation before its first save**. It cannot be edited later. PostgreSQL composite unique indexes enforce `(slug, locale, section)` and `(translationKey, locale)`. Slugs allow lowercase ASCII letters/numbers with single hyphens. Locale is exactly `ar` or `en`; sections are history/regions/people/heritage. Slug, locale, section and title are sensible identity fields required to save; body/citations/category/summary are not required until approval. No hidden opaque input is required to create a draft.

Workflow: draft → factual-review → translation-review → approved; `_status` remains Payload's normal draft/published field. Review stages are editorial labels, not mandatory sequential gates. To approve, a reviewer/administrator must explicitly submit `reviewStatus=approved`; the server records their ID and current timestamp and requires title, summary, category, a complete body section and a complete HTTP(S) citation. Incomplete fact rows must be completed or removed. URLs with embedded credentials or non-HTTP(S) schemes are rejected. Approval does not verify the truth or licensing of a source: that is the human review responsibility.

Publish only after approval. Client-supplied audit fields are ignored. Substantive fields include SEO title, description, canonical URL and noIndex. Non-reviewer substantive edits to approved/published articles reset review status and publication to draft and clear audit fields, including saves carrying stale approved/published values. Reviewer changes also reset approval unless the request explicitly approves the new content. To avoid Payload's usual “new draft, old published version still live” behavior, create/update `draft=true` is normalized to a main-document draft save. **Saving a draft unpublishes immediately**, and main-table unique indexes apply to draft edits too. Version history is retained (50 versions). Normal version restoration requires reviewer/admin and passes the same workflow hooks; draft-only restoration is rejected so it cannot leave an old publication live. To restore privately, unpublish first, use normal restore, and ensure the restored version is draft before publishing.

Sources is a private research library. Article `sources` arrays are intentionally standalone public citations, not relationships to potentially private research notes. Keep the two translation documents' facts/body rows in matching order, and their source URLs identical and in matching order. `period` and `kind` must be shared values (period should be language-neutral, e.g. `1932–1953`). The public adapter returns **only complete ar/en pairs** with matching translationKey, section and slug, aligned body/fact/source arrays, shared period/kind and the same media relationship ID (or neither). Featured is true only when both translations select it.

`Articles.read` performs a deliberately privileged, read-only `payload.db.find` against **main article documents**, with a fixed approved/published predicate and explicit projection of pairing/content fields. It does not invoke the Local API recursively, populate relationships, use a client-set recursion flag, query versions, return private audit fields, or accept the request's query as its internal filter. `req` preserves transaction context. Runtime decoding checks the selected unknown documents, then only complete matching pair IDs are returned as an access `Where` combined with the publication predicate. Orphans, mismatches and duplicate locales have no eligible IDs. An empty ID filter gives an empty inventory rather than throwing an access-denied error. Staff retain their existing editorial access. Malformed published records and adapter failures fail closed; they do not enable unrestricted access or demo fallback.

The public Local API adapter also runtime-decodes its results before array access and verifies canonical identity, duplicate locales/routes, structure and image agreement again. Orphans are omitted; inconsistent pairs that reach this boundary throw a non-content-bearing data-integrity error rather than silently selecting one document or returning demo content. This is structural validation, not proof of factual accuracy or equivalent translations.

`getCMSEntries()` queries every approved published page in batches of 100, explicitly using `overrideAccess:false`, `user:null`, `draft:false`. It does not memoize or hide errors. `null` is exclusively “not configured”; `[]` is a configured CMS with no eligible pairs. The frontend must distinguish them, propagate database errors, and use `force-dynamic` without public data caching. Do not wrap this function in `cache`, `unstable_cache` or `use cache`. Already delivered pages/downloads cannot be revoked, and an in-flight paginated read is not a transactional snapshot.

The access check scans eligible main documents afresh on each access invocation, including each Local API page. This favors immediate next-request unpublishing over throughput; it is not a scalable SQL join or a cross-request cache. Pair eligibility and the subsequent read are separate queries: a concurrent change between them can race, so strict atomic pair visibility requires a future transaction/snapshot or database-level query design, verified on staging. There is no claim of atomic revocation for in-flight requests.

## Media and storage

Uploads accept single-frame JPEG, PNG, WebP and AVIF images only, not SVG or animations. Authentication is required before image decoding. Client-supplied filenames, storage URLs, prefixes and metadata cannot change a stored file's identity; crop/focal edits use server-read metadata and revoke public delivery without explicit reviewer approval. URL-paste uploads are disabled. Images are decoded/validated and re-encoded as WebP, resized inside 2400×2400; upload limit is 10 MiB. Attribution, license and alt text are required. Media is readable only by editorial users unless its `published` flag has been explicitly authorized by reviewer/admin. Non-reviewer replacement/metadata edits revoke an existing public flag. Article approval does not automatically publish media. Both article translations must reference the same asset. Public rendering uses it only when both populated relationships are released, their delivery paths agree and both article image descriptions are supplied. Only same-origin `/api/media/file/<filename>` URLs without credentials, queries or fragments are accepted; direct object-store URLs are declined. Private/unavailable images or absent bilingual descriptions use `/images/diriyah.jpg` with explicit Arabic/English alt text describing contextual earthen architecture in Diriyah, **never** the person's title. Fallback asset provenance and required credits are recorded in `docs/asset-licenses.md`.

Configure **all four** `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` to enable S3. `S3_ENDPOINT` and `S3_FORCE_PATH_STYLE=true` support compatible providers. Partial configuration is an error. Production with a configured CMS refuses local storage: ephemeral disks, deployments and multiple replicas make it unsafe.

Keep the bucket private with public-access blocking and least-privilege credentials limited to the media bucket. Do not enable public ACLs, direct public URLs, signed-download redirects or `disablePayloadAccessControl`. S3 files are delivered through `/api/media/file/...` after Payload access checks. Direct client uploads are off. REST/file responses are `private, no-store` with `nosniff` on image delivery. Do not put a caching CDN/proxy or Next image optimization cache in front of protected media URLs: use unoptimized public `<img>` delivery or explicitly disable optimization in the frontend. Purge any pre-existing caches when changing access. Authorized users can still save downloaded bytes.

The storage plugin adds a persisted `prefix` only when that option is configured. This project currently uses no prefix, preserving the existing filenames as object keys. If prefix, image sizes or storage fields change later, review schema differences with the same storage configuration on staging before applying a migration.

On 2026-09-23 the operator authorized creating the private Supabase bucket `saudiapedia-media` and copying the current media inventory. All 38 registered WebP files were copied, compared by size and SHA-256 after authenticated S3 reads, and subsequently verified through anonymous Payload `/api/media/file/...` delivery with no-store/nosniff headers. Direct anonymous S3 and public-storage-URL access was denied. Bucket metadata confirms `public=false`, a 10 MiB limit and a closed list of raster MIME types; no Storage client RLS policies were added. No CMS records or publication states were changed.

Supabase-generated S3 keys are project-wide and bypass RLS; keep them server-only in this dedicated project. The existing Windows launcher reads the optional DPAPI-protected `s3-credentials.xml` alongside its existing credential vault, not from a repository dotenv file. `powershell.exe -NoProfile -File scripts/storage-local.ps1 -Action verify` rechecks the stored objects without uploading. `-Action copy` is an explicitly authorized operator action, not a deploy hook; it reads the media inventory, rejects conflicting files, sends conditional object creation, and never deletes source files or updates CMS documents. Do not run concurrent copies or erase local backups.

## Production migrations and deployment

Production always sets adapter `push:false`; never run development schema push against production. The repository contains the existing migration history under `src/collections/migrations/`. The selected Render deployment reuses the existing Supabase database and does not run migrations or seed jobs automatically. Do not regenerate or apply an initial baseline to this populated database.

1. Use a clean dedicated PostgreSQL database for migration generation, configure S3 and `CMS_DB_PUSH=false`, and load the server environment securely. The installed Payload 3.89 CLI uses `@next/env` and loads `.env.local` plus the appropriate development/production env files from the working directory. Existing shell variables take precedence. Run from the project root and verify the target database without printing credentials; never commit real env files. Set `PAYLOAD_CONFIG_PATH=src/payload.config.ts` if automatic discovery fails.
2. Run `npx payload migrate:create initial` using the already-installed CLI. Inspect generated SQL and commit files under `src/collections/migrations/`. Verify both composite unique indexes, the unique nullable users bootstrap key, all version tables and the S3 prefix field. Do not generate a baseline against a database already pushed to the desired schema and assume it initializes an empty database.
3. Back up production database **and private media**; rehearse restoration and migration on staging with production-equivalent configuration. Run `npx payload migrate:status`, then `npx payload migrate` as a single controlled deployment job, using credentials permitted to change the schema. Runtime app credentials can be less privileged.
4. Deploy only after migration succeeds. Configure secrets in the hosting environment, persistent private S3, HTTPS and same-origin proxy forwarding. Production imports require S3 and CMS_SERVER_URL as well as database/secret values, including build/CLI contexts that load the config. Do not inject fake build credentials.
5. Bootstrap privately, then run role/access tests. Verify anonymous article/version/media/source behavior, attempted role escalation, stale-status editor saves, both unique constraints including draft edits, simultaneous first-register requests, reviewer audit identity, restore permissions, unpublish visibility, upload restrictions, and bilingual pairing. Add edge rate limits for login/bootstrap/API and monitor failed auth, DB errors, storage and migrations. No rate-limiter infrastructure is configured here.

GraphQL is disabled; the requested usable API is REST. No GraphQL playground route is provided. Scheduled publication, custom previews, mail, malware scanning, migrations, backups and production infrastructure are not supplied. Type/lint checks alone do not verify database transactions, S3 permissions or authentication workflows. The limited storage verification recorded above is not a full authenticated staging audit or a successful Render deployment.

## Focused safety regression tests

`tests/unit/cms.test.ts` uses `node:test`, relative imports, unknown-document fixtures and typed read doubles. It covers empty/partial/weak configuration, pagination and Local API access flags, malformed documents, canonical mismatches/duplicates, nonrecursive anonymous pair filtering, next-request unpublishing, image URL/alt safety, error propagation, admin font imports and noindex source contracts. Run directly with the installed Node/tsx unit runner when coordinated with other checks. These tests do not connect to PostgreSQL/S3 or validate the configured admin in a browser.

The full unit suite includes paired-ID access doubles, authentication/media workflow guards, deployment-environment validation and bounded HTTP tests. Browser tests deliberately disable CMS and verify both locales plus browser-enforced CSP. They do not create users or modify the current database.

## Render runtime

The Blueprint is `.devin/render.yaml`; set that custom Blueprint Path while keeping the service root at the repository root. See README for the dashboard steps and secret variables. `render:build` supplies the canonical HTTPS origin but removes CMS/storage credentials from the Next build child process. `render:start` requires the runtime-only database role, a stable Payload secret, private S3 configuration, a verified CA certificate file and a stable Server Actions encryption key. It rejects an origin or Server Actions key that differs from the build manifest and binds to `0.0.0.0:$PORT` (default 10000).

`CMS_REQUIRED=true` prevents a misconfigured deployment from silently serving editorial previews. `/api/health` is a read-only readiness check: it validates production settings and probes the database for an administrator and core tables, returning only ok/unavailable with no-store. It coalesces concurrent checks and bounds the HTTP wait. It does not prove S3 object availability, live login, editorial completeness, backups or end-to-end provider transport; verify these separately before launch. Changing a custom domain requires a rebuild, not only a runtime environment change.
