## Security controls and safe verification

- The 2026-09-23 security work is restricted to isolated tests by the operator. Do not run account guessing, upload probes, database migrations, or mutating security tests against the existing CMS. A real authenticated staging/PostgreSQL/S3 integration test remains separate from unit and CMS-disabled browser tests.
- Keep Payload packages aligned at 3.89.0. DOMPurify 3.4.15 and the scoped esbuild 0.25.12 override address known dependency advisories. Do not remove security overrides or use force/legacy-peer-deps to bypass resolution. `npm audit` checks known advisories, not overall application security.
- Bootstrap is closed by default. Use `CMS_ALLOW_BOOTSTRAP=true` only temporarily behind a private operator gate for the first account, then remove it. New passwords require 15–128 characters; changing a password clears sessions. Existing passwords/accounts are not automatically changed. Forgot/reset-password operations are disabled until a real mail integration and recovery review are provided.
- SEO fields are public content and now require renewed editorial approval when changed. Media storage identities are server-controlled; crop/focal changes revoke stale public release. Uploads are single-frame raster images, capped at 10 MiB and 40 million input pixels. Do not weaken these checks to accommodate invalid files.
- Next image optimization accepts only static `/images/**` and `/brand/**` URLs without queries. Never allow `/api/media/file/**` into that shared cache. Page CSP uses per-request nonces from `src/proxy.ts`; JSON-LD carries the server nonce. Test injected HTML in a browser response, not scripts inserted by privileged DevTools evaluation.
- REST request bodies are limited to 256 KiB, or 12 MiB for multipart media requests, with a 30-second read deadline; the analytics body has its own 512-byte limit and deadline. Anonymous list reads are paginated at at most 100 records with bounded depth; section navigation paginates internally. These limits do not replace distributed edge rate limiting or DDoS protection.
- Database provisioning/inspection uses the operator-only `CMS_DATABASE_ADMIN_PASSWORD` environment variable. Never read a password from `.env.example` or commit environment files. The local launcher strips that administrator variable from web, smoke and migration child processes. Historical plaintext copies, if present, must be handled and rotated by the operator; this audit did not read or modify them.
- Open security item: Payload 3.89.0 native password generation and verification still use PBKDF2-HMAC-SHA256 with 25,000 iterations. This is below the current OWASP PBKDF2-SHA256 recommendation (600,000); the stronger password-input policy does not change stored hashing. Do not patch vendor constants or silently invalidate existing accounts. A versioned authentication/hash migration or an identity-provider integration requires operator approval and separate staging verification.
- For isolated builds/tests, explicitly clear `DATABASE_URL` and `PAYLOAD_SECRET` and keep `CMS_DB_PUSH=false`. Review deployment TLS, private storage, backups, MFA/SSO, edge limits, and secret rotation separately; no live-host or database-security certification is implied by passing local tests.

Missing/unavailable cache is optional and does not abort the wrapper. Use normal Deploy latest commit for warm builds; Clear build cache forces a cold build. Cache tests are included in `tests/unit/production.test.ts`.

Storage transfer is separate from deployment and uses the current CMS filenames, read-only SQL and byte verification. Preserve existing local images as backups; never rerun copy blindly or overwrite conflicts.
