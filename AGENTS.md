## Security controls and safe verification

- The 2026-09-23 security work is restricted to isolated tests by the operator. Do not run account guessing, upload probes, database migrations, or mutating security tests against the existing CMS. A real authenticated staging/PostgreSQL/S3 integration test remains separate from unit and CMS-disabled browser tests.
- Keep Payload packages aligned at 3.89.0. DOMPurify 3.4.15 and the scoped esbuild 0.25.12 override address known dependency advisories. Do not remove security overrides or use force/legacy-peer-deps to bypass resolution. `npm audit` checks known advisories, not overall application security.
- Bootstrap is closed by default. Use `CMS_ALLOW_BOOTSTRAP=true` only temporarily behind a private operator gate for the first account, then remove it. New passwords require 15–128 characters; changing a password clears sessions. Existing passwords/accounts are not automatically changed. Forgot/reset-password operations are disabled until a real mail integration and recovery review are provided.
- SEO fields are public content and now require renewed editorial approval when changed. Media storage identities are server-controlled; crop/focal changes revoke stale public release. Uploads are single-frame raster images, capped at 10 MiB and 40 million input pixels. Do not weaken these checks to accommodate invalid files.
- Next image optimization accepts only static `/images/**` and `/brand/**` URLs without queries. Never allow `/api/media/file/**` into that shared cache. Page CSP uses per-request nonces from `src/proxy.ts`; JSON-LD carries the server nonce. Test injected HTML in a browser response, not scripts inserted by privileged DevTools evaluation.
- REST request bodies are limited to 256 KiB, or 12 MiB for multipart media requests, with a 30-second read deadline; the analytics body has its own 512-byte limit and deadline. Anonymous list reads are paginated at at most 100 records with bounded depth; section navigation paginates internally. These limits do not replace distributed edge rate limiting or DDoS protection.
- Database provisioning/inspection uses the operator-only `CMS_DATABASE_ADMIN_PASSWORD` environment variable. Never read a password from `.env.example` or commit environment files. The local launcher strips that administrator variable from web, smoke and migration child processes. Historical plaintext copies, if present, must be handled and rotated by the operator; this audit did not read or modify them.
- Open security item: Payload 3.89.0 native password generation and verification still use PBKDF2-HMAC-SHA256 with 25,000 iterations. This is below the current OWASP PBKDF2-SHA256 recommendation (600,000); the stronger password-input policy does not change stored hashing. Do not patch vendor constants or silently invalidate existing accounts. A versioned authentication/hash migration or an identity-provider integration requires operator approval and separate staging verification.
- For isolated builds/tests, explicitly clear `DATABASE_URL` and `PAYLOAD_SECRET` and keep `CMS_DB_PUSH=false`. Review deployment TLS, private storage, backups, MFA/SSO, edge limits, and secret rotation separately; no live-host or database-security certification is implied by passing local tests.

Preserve existing local images as backups; never rerun copy blindly or overwrite conflicts.

## CMS MCP server for AI agents (2026-09-28)

- `POST /api/mcp` (`src/app/(payload)/api/mcp/route.ts`) is a stateless MCP Streamable HTTP endpoint (JSON responses, protocol versions 2025-11-25/2025-06-18/2025-03-26, no sessions, no SSE, no batching). It is implemented without the MCP SDK to avoid adding express/hono/cors and other transitive dependencies: `src/mcp/protocol.ts` (JSON-RPC, rate limits), `src/mcp/schema.ts` (strict validators that also emit the advertised JSON Schema), `src/mcp/tools.ts` (tools).
- It returns 404 unless `MCP_ENABLED=true`; local staging sets it, production does not until the operator decides. Operator choices on 2026-09-28: remote endpoint, full access including publishing, existing CMS accounts. Authentication is `Authorization: Bearer <Payload JWT>` only — only that header is passed to `payload.auth`, so browser session cookies never authenticate MCP calls. Tokens come from `node scripts/mcp-token.mjs [--url …]` (prompts for email/hidden password, prints a 2-hour token and a client config; nothing is stored). 3 failed logins lock the account for an hour. Recommend a dedicated reviewer-role account per agent rather than a personal administrator.
- Long-lived agent key (operator request 2026-09-29): `node scripts/mcp-key.mjs` prints a `ksmcp_…` key once and its SHA-256. Render stores only `MCP_API_KEY_SHA256` plus `MCP_AGENT_EMAIL` (the CMS account the key acts as); `src/mcp/api-key.ts` compares digests in constant time and refuses missing, locked or administrator accounts (editor/translator/reviewer only; use reviewer to publish). The key does not expire: rotate it by generating a new key and replacing the hash; changing the account password does not revoke it. Short-lived session tokens from `mcp-token.mjs` keep working. Verified on staging with a reviewer account (`mcp-reviewer@staging.local`): whoami, wrong-key 401, create, publish, public page, unpublish (6/6). Two unpublished test drafts (`heritage/mcp-key-test`, IDs 130–131) remain in local staging.
- Every tool runs through the Payload Local API as that user with `overrideAccess: false`, so roles and the editorial workflow apply exactly as in the admin panel: editors create/update drafts, only reviewer/administrator accounts can `publish_article`; content edits unpublish until re-approved. Pair writes (Arabic+English) run in one database transaction. Writes require `expectedUpdatedAt` from `get_article` (optimistic concurrency); publish/unpublish also require `confirm: true`; publishing runs `review_checklist` first. There are deliberately no delete, account, password or media-upload tools. Article text is returned as untrusted data (stated in the server instructions).
- Images (operator request 2026-09-30): `create_article`/`update_article` accept `image` (existing media ID shared by both translations, `0` clears it; the ID must be readable by the account) and `search_media` lists media with their `published` flag. Uploading stays admin-panel only. `review_checklist`/`publish_article` refuse an article whose image is not approved for public delivery, because private media silently disappears from public pages (any media edit resets `published`, see `enforceMediaPublication`).
- First production MCP publication (2026-09-30, operator request): the `agent` account (user 2) was changed from editor to reviewer by the operator; `create_article` → `update_article` (image) → `publish_article` published `people/mohammed-bin-salman` (article IDs 133–134, translation key `people-20260930-mohammed-bin-salman`, category «ولاة العهد» / “Crown princes”, `kind=notable`) from `docs/editorial-batches/people-mbs-20260930.json` with Saudipedia/SPA sources only. The key used was pasted into the chat; rotate it with `mcp-key.mjs`.
- Guards: Origin must be absent or the site origin (DNS rebinding), `Content-Type: application/json`, 256 KiB body limit, `MCP-Protocol-Version` validation, per-account rate limits (60 calls and 20 writes per minute, per instance), no-store/nosniff/noindex headers, internal errors reported generically. Each call logs tool, user ID, role, outcome and duration via `payload.logger` without content or tokens; Payload versions hold the edit history.
